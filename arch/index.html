Vitalos Technologies · Architecture

Vitalos platform

The public website at vitalos.co.uk and the internal Super Admin and client portal, in one monorepo. The website runs on Vercel with a Supabase database. The Super Admin is a separate Django application on Google Cloud Run with its own database. The two share no code or data and talk only through signed APIs.

Front end

Next.js 16 website

React 19 and Tailwind 4. Pages come from one route manifest; repo content is static per deploy. The Relay widget loads its panel only when a visitor opens it.

Back end

Route handlers and Django apps

Server actions and route handlers with zod and ports and adapters on the website; 20 Django apps in the Super Admin, from enquiries to the client portal.

Data

Two PostgreSQL databases

Supabase for the website (RLS, pgvector, pg_cron) and a separate Super Admin database. Files live in Cloudflare R2.

Platform

Vercel, Cloud Run, Cloudflare

Vercel in dub1, Cloud Run in europe-west2 scaled 0 to 1, Cloudflare for DNS, Workers and R2. GitHub-hosted runners only.

AI

Two model paths

Relay uses DeepSeek behind a swappable interface with redaction first. AI & Data uses Anthropic through the aicore gateway with a kill switch and caps.

Security

Signed, scoped, scanned

HMAC-signed APIs between the apps, TOTP for staff, OIDC deploys with no stored cloud keys, CSP, gitleaks, CodeQL and a client-bundle secret scan.

Key flows

The journeys that matter most, step by step.

Security

Trust boundaries, authentication and authorisation, secrets handling and data protection, at design level. The full threat model is docs/security/threat-model.md.

Auth

Staff and clients

  • Email and password with lockout (django-axes)
  • TOTP required for SuperAdmin and anyone who enrols
  • 8-hour HttpOnly sessions; host-only cookies split admin and portal
Access

Authorisation

  • Roles: SuperAdmin, ServiceLead, Viewer
  • Record classifications limit who sees what
  • Portal users see only their organisation's published records
Machines

Service to service

  • HMAC-SHA256 with per-scope key lists and a 300-second window
  • Hashed Bearer tokens for the read API
  • OIDC from GitHub Actions to Google Cloud
Secrets

Where they live

  • Vercel environment variables for the website
  • GitHub production and backup environments for deploys and backups
  • Google Secret Manager at runtime; Cloudflare Worker secrets
Privacy

Data protection

  • IP addresses stored only as HMACs
  • Retention: enquiries 24 months, Relay nightly purge, applications six months
  • Relay redacts before every model call; AI & Data stores metadata and hashes only
Pipeline

Supply chain and browser

  • Pinned actions, Dependabot, pnpm audit, pip-audit, bandit, CodeQL, gitleaks
  • Client-bundle secret scan; @vitalos/config is server-only
  • CSP, frame-ancestors 'none', noindex outside production

Documentation drift

ARCHITECTURE.md describes the state of 10 Oct 2026: it says no remote Supabase project is used and lists only enquiry data. The Relay knowledge workflow now writes to a production Supabase project, and Relay, Insights, Careers, AI & Data, billing and the portal have landed since.
docs/architecture/container-architecture.md shows Vercel as the "intended host; previews blocked", while the README says the site is live on Vercel.
ADR-042 and parts of superadmin/docs/DEPLOY.md still describe Azure (for example a Container Apps job) after the move to Cloud Run on 1 Nov 2026, and the deploy guide's status line still reads "Not live yet".
The ADR index says it was last reviewed on 10 Oct 2026 but lists ADRs up to 056. ADR-029, ADR-044 and ADR-045 are still marked Proposed although their code is in the repository.

Open risks

One instance, free-plan data

The Super Admin runs at most one Cloud Run instance on a free-plan database. Nightly encrypted dumps are the only copy outside the provider.

Two assistants behind one switch

Relay and the Askbridge widget both stay in the code, selected by a build-time key. Both paths need to keep passing their e2e suites.

Shared production environment

The website and the Super Admin share the GitHub production environment. Distinct secret names keep their values apart.

Inbound mail and portal domain

The Email Worker is prepared but not deployed, and the portal domain binding is pending. Both are owner steps.

Retention in dry run

Application retention logs counts until a person switches enforcement on.

Model data exposure

Relay's redaction is pattern based, and AI & Data relies on input limits rather than redaction.
